# 规划文档 ↔ 实现 对照表

对照对象：飞书《Ontology Studio 平台建设规划：以 Harness 工程为核心》（revision 74）

**核对程度**：结构层已核对——26 个标题与 block ID 与项目启动时的快照逐一对上，
说明文档没有被增删改标题。正文层未做逐段比对（对比方法受 markdown 格式差异影响）。

下面按「文档怎么说 / 实现到哪 / 建议怎么归类」三列列出。分类只有三种：

- **已实现**：有后端、有校验、能改，不只是界面
- **半实现**：能做一半，或只有界面没有真实数据
- **未实现**：后端一行代码都没有

## 一、已实现（可以对外承诺）

| 文档要求 | 实现情况 |
| --- | --- |
| 统一的 Ontology IR | `*.ir.json` 声明式定义，JSON Schema 校验，未知字段会被拒绝 |
| 本体模型设计中心 | 对象/属性/关系/规则/动作全生命周期，面板可建改删 |
| 四视角（业务/数据/技术/AI） | 已实现，技术视角有 `storage` / `indexed` 字段（示例值） |
| 逻辑与动作 | 规则在示例数据上真求值；动作真执行，有前置校验与事后回验 |
| 审批闸门 | 写操作经 Host 审批；拒绝即不写盘 |
| Harness 工具体系 | 32 个工具，读写分离，只读模式下写工具不注册 |
| 执行轨迹 | `*.ontology-traces.jsonl`，面板按 Agent 汇总声明与证据 |
| 资产市场 | 目录、安装、卸载、升级、版本对比 |
| 插件化 | 以 DSH 插件形式挂载，宿主半 + 客户端半 |
| 可观测与评测 | 评测记录条件指纹，条件不一致拒绝比较 |
| 指标口径 | IR 里声明（count/sum/avg/min/max + 过滤表达式），在事实数据上真算，返回「多少行参与」；**无时间窗口、无多维下钻** |
| 业务流程编排 | IR 里声明步骤（检查规则/指标、演算动作、人工闸口），`ontology_process_plan` 在事实数据上推演：会不会卡、卡在哪、哪步要人确认；**是推演不是工作流引擎**——无运行实例、无定时/重试/补偿 |

## 二、半实现（文档需要降级描述）

| 文档要求 | 现状 | 建议写法 |
| --- | --- | --- |
| Data Studio 数据接入 | CSV 这条路是通的：读文件 → 推断列类型 → 装成资产包 → 记录同步状态（时间/行数/列结构变化）；**但仍是单文件拉取式，无调度、无增量，行数据不落成本体事实** | 改为「支持 CSV 快照接入与同步状态；行级同步、调度与 CDC 待建设」 |
| App Studio 应用构建 | 能生成规格，面板新增**只读渲染预览**：列表/筛选/排序/详情都读真实事实数据；**写操作（新增/编辑行）与动作执行仍走 Agent** | 改为「按本体元数据渲染只读应用视图；写入与动作执行经 Agent 审批」 |
| Marketplace | 能力齐全，但面板只读，写操作走 Agent | 改为「资产市场通过 Agent 操作，面板只读」 |
| Governance 治理 | 有校验/发布/历史/级联/审批；**视图（角色视角）可声明、可校验、可按视角读取与导出，但它是输出裁剪而不是鉴权**——没有会话身份，不传 view 仍是全量 | 改为「治理含校验、审批与角色视角声明；数据级读权限的执行依赖宿主身份」 |

## 四、为什么建议这样收窄

平台的目标没变，但**先把能兑现的部分说清楚**比全部承诺更可信：

1. 文档承诺的十项里，实现只有四项是完整的
2. 半实现的四项如果不降级描述，演示时会被当成 bug
3. 未实现的七项如果留在「核心功能」里，评审时很难解释

**收窄不是缩小目标**，是把「已交付」和「计划中」分开，让读者知道现在能用什么。

## 五、建议的后续顺序

| 优先级 | 动作 | 理由 |
| --- | --- | --- |
| P0 | 文档按上表降级 / 移入规划 | 立刻消除「文档与实现不一致」 |
| P1 | 数据源接入最小闭环（读一张真实表 → 生成本体草稿 → 记录同步状态） | 补最大短板，让 Data Studio 不再是空壳 |
| P2 | 角色 + 数据级读权限 | 上生产的前提 |
| P3 | App Studio 渲染器 | 有真实消费方时再做 |
